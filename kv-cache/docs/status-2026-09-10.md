## 1. Where the framework stands

**Assumed correct, not yet validated correct.**

R3.15 fixed a defect that was silently serving KV belonging to a *different prompt*. With
it in place, every check that has been run passes, and the two independent instruments
that previously disagreed with each other now agree. That is enough to work on and enough
to benchmark against, so the framework is treated as correct from here.

It is **not** enough to call it validated. §4 lists what is still required, and none of it
is optional before any accuracy claim is made from this repository.

## 2. What was wrong

`A1` in `kv-cache-known-issues.md` recorded, as CRITICAL, that "cold" prefill runs were
self-caching: a BetterBench sweep that salts every prompt with a fresh nonce was measuring
prefill ~2.3x faster than a true cold run.

The root cause recorded on 09-09 was: *"vLLM radiance matches the prefix cache by block
content, not by chained prefix."* **That is wrong.** The GPU prefix cache chains
correctly and always did. The defect was in the **offload tier's** lookup: pre-R3.15, the
mixed-hit path could hand `prepare_load` a key it had not confirmed, so the tier matched
blocks whose *content* was identical while their *chained prefix* was not.

Why that is a correctness bug and not just a fast benchmark: the nonce changes only block
0. Blocks 1..N are byte-identical text across every prompt in the sweep — but their KV was
computed under a different preceding context. Chained block hashes exist precisely to
poison those keys. Serving them substitutes another prompt's KV into the answer.

## 3. The evidence — a controlled reverse test

Run twice on the same box, same model, same corpus, same eight depths, warmup 2 + 8
measured passes, **one variable**: `patch_offload_mixed_hit.py`, fixed vs `a48e3a7^`.
`KVOFF_PENDING_IS_MISS=0` was held identical in both arms and confirmed live in the boot
check (`77 hunks applied, 0 failed`), so the one configuration change made between the two
historical runs could not account for the difference.

**Arm A — R3.15 present.** Prefill matched the independent cold baseline within **1.3% at
all eight depths**, the curve is monotonic in depth again, and TTFT spread fell to
**0.05–0.35%**. A probe replicating the harness's prompt construction byte-for-byte showed
a new nonce recomputing in full (0 GPU hits, 0 external hits, 45 s) while an exact repeat
hit 92,288 tokens in 1.5 s — so the instrument is not blind, the nonce holds.

**Arm B — R3.15 absent.** 60-second window at the deep end of the same sweep:

| metric | delta over 60 s |
|---|--:|
| `external_prefix_cache_queries_total` | +188,192 |
| `external_prefix_cache_hits_total` | **+184,576 (98.1%)** |
| `prefix_cache_hits_total` (GPU) | **+0 (0.0%)** |
| `kv_offload_load_bytes_total` | +6.44 GB |

The GPU cache and the tier are looking at the *same prompts in the same window*. The GPU
cache refuses all of them. The tier serves 98.1%. That asymmetry is the bug, isolated.

The earlier symptom is reproduced on demand: a prefill sweep in which nothing may
legitimately hit ran ~50% faster than the fixed engine's honest rate at the same depth.

**A measurement trap worth carrying forward:** the probe that "cleared" the nonce was run
on the *fixed* engine. The bug is invisible to any probe run on patched code. Arm the
defect before concluding that a cache respects a salt.

## 4. What is still required for correctness validation

Ordered by what blocks what. None of this is done.

1. **Output correctness under the armed defect.** Hit-rate and timing show the tier serves
   mis-chained KV; showing the *generated tokens differ* from a known-good recompute is
   what makes it a demonstrated wrong-output bug rather than an inferred one. This is the
   form upstream will want. Needs the defect re-armed and two model reloads.
2. **Re-run the A1 A/B on the fixed engine.** The 09-09 measurement — repeating body
   9.1 s / 3,520 t/s against unique body 20.6 s / 1,555 t/s — was taken on defective code.
   On a correct engine the two should converge. Until that is re-measured, the size of the
   pollution in the historical runs is unknown, only its direction.
3. **Replace the polluted BetterBench full run.** All three phases, fixed engine. Every
   number in the existing full run was taken with the defect live and stays uncitable.
4. **A negative control for `mixedbench.py`.** It has never been shown to fail when it
   should. A harness that has only ever passed has not been tested.
5. **Stock reproduction.** Both R3.15 defects are argued to be present in unmodified vLLM
   0.27.1, but that has not been demonstrated on a stock build. This blocks filing
   upstream, and no upstream report should be made without it.
6. **Accuracy under the stride store (A2/D4).** Independent of R3.15 and untouched by it.
   The N=8 stride is approximate *by design*; its accuracy cost is still unmeasured.

## 5. What this does not change

- The stride store is still approximate at non-boundary positions (`A2`, `D1`, `D4`).
  R3.15 has nothing to do with that and does not improve it.
- Storage density is still at the architectural floor.
- The concurrency policy is unchanged: one long request at a time.
- **Every benchmark number produced before 2026-09-10 remains uncitable** — not because
  the harness was wrong, but because the engine under it was.
